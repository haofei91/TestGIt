## 二、核心架构分类

### 2.1 MCP 工具层（被动工具，由外部 AI 调用）

| 项目 | 说明 |
|------|------|
| **mobile-mcp** | 纯工具层，Robot 接口统一 Android/iOS，20+ Tool，不含任何 LLM 逻辑 |
| **android-mcp-server** | 极简 MCP Server（2 个文件），直连 ADB，25 个 Tool，持久化 Shell 优化 |
| **Android-MCP (CursorTouch)** | 基于 uiautomator2 的 MCP Server，14 个 Tool，u2 Selector 查找 + 等待元素 |
| **appium-mcp** | 基于 Appium WebDriver 的 MCP Server，13 个 Tool（实际实现），10 种定位策略 |
| **claude-in-mobile** | 全平台 MCP Server（5 平台），~40 个 Tool，130+ 别名，Flow 引擎，功能最全 |

### 2.2 自治 Agent（内置 LLM 推理循环）

| 项目 | 说明 |
|------|------|
| **droidrun** | 完整 Agent 框架，Manager/Executor/FastAgent 三模式，Portal App 架构，多 LLM 支持 |
| **Open-AutoGLM** | 端到端自主 Agent，内置 ChatGLM VLM 推理，三平台支持（Android + HarmonyOS + iOS） |
| **AppAgent** | 学术研究原型，两阶段（探索-利用）架构，自动生成 UI 文档，GPT-4V/Qwen-VL |

### 5.2 元素交互模型分级

```
Level 0 — 纯坐标驱动
    AI 看截图 → 推算坐标 → input tap x y
    代表：Open-AutoGLM（核心方式）

Level 1 — 截图标注 + 坐标
    截图上标注编号 → AI 选编号 → 查表得坐标 → input tap x y
    代表：AppAgent（SoM 数字标注）、droidrun（IndexedFormatter）

Level 2 — UI 树 + 坐标
    uiautomator dump → 解析 XML → 返回元素列表(含坐标) → AI 选坐标 → input tap
    代表：mobile-mcp、android-mcp-server（基础版）

Level 3 — 元素属性查找 + 坐标
    获取 UI 树 → 按 resource-id/text/content-desc 查找 → 取中心坐标 → tap
    代表：android-mcp-server（tap_element）、claude-in-mobile（input_tap + text/resourceId）

Level 4 — 原生 Selector 查找 + 操作
    u2 Selector / Appium Locator → 原生 API 查找元素 → 原生 click()
    代表：Android-MCP (u2 Selector)、appium-mcp (10 种 Appium 定位器)

Level 5 — 模糊匹配 + 置信度
    输入自然语言描述 → 多维评分匹配 → 超过置信度阈值 → 自动点击
    代表：claude-in-mobile（ui_find_tap，0-100 评分）
```

## 八、每个方案的优劣势

### 8.1 mobile-mcp

**优势：**
- 双平台（Android + iOS）真机 + 模拟器全覆盖，覆盖面最广
- 纯工具层设计，与外部 Agent 解耦最干净
- 支持 `--listen` SSE 网络模式，适合 CI/云端
- 安全防线完善（包名正则、路径白名单、URL 协议限制、Zip-Slip 防护）
- Robot 接口抽象优雅，扩展新平台只需实现接口
- 截图自动压缩，LLM 友好
- Star 最高（4.5k），社区活跃，更新频繁

**劣势：**
- 无元素属性查找能力（只能坐标点击，不能按 text/id 点击）
- 无等待元素机制
- 无 Shell 命令执行
- Android 非 ASCII 输入依赖额外安装 DeviceKit
- 同步 execFileSync 可能阻塞
- 无 Flow/批量命令能力

---

### 8.2 android-mcp-server

**优势：**
- 极简设计（2 个文件 ~1200 行），认知负担最低
- `npx -y android-mcp-server` 一行启动，部署最快
- 持久化 Shell 减少进程创建开销，性能最优
- 复合操作（`tap_sequence`、`tap_and_wait`、`scroll_to_element`）减少 AI 交互轮次
- 元素查找支持 resource-id/text/content-desc（含子串匹配）
- 25 个 Tool 数量丰富，含日志/设备管理
- `adb_shell` 万能逃生舱

**劣势：**
- 仅支持 Android
- 正则解析 XML 不够健壮
- `input text` 不支持中文
- 无 iOS 支持
- `__MCP_DONE__` 标记可能与命令输出冲突

---

### 8.3 Android-MCP (CursorTouch)

**优势：**
- u2 原生 Selector 查找（text/resourceId/className/description），元素操作最可靠
- WaitForElement 原生等待元素出现
- 拖拽操作（Drag）——唯一支持的方案
- 懒连接设计，Server 启动不要求设备在线
- 截图量化（256 色）减少 token 消耗
- 并行采集（XML + 截图 threading）

**劣势：**
- 仅支持 Android
- Python 3.13 严格限制
- 需要设备端 ATX Agent（u2 自动安装）
- 无应用管理能力
- 无 Shell 命令
- 无剪贴板操作

---

### 8.4 appium-mcp

**优势：**
- **10 种定位策略**（id/xpath/accessibility_id/ios_predicate/ios_class_chain/image 等），最丰富
- 基于 Appium 成熟生态，设备兼容性最好
- Python asyncio 异步架构 + 会话池 + 异步锁，并发安全
- 结构化异常体系（16 种异常类）
- CLI doctor 命令自动检查环境
- 跨平台（Android + iOS）

**劣势：**
- 需要额外运行 Appium Server 进程，部署链最长
- 实际只实现 13 个 Tool（声称 40+）
- 无坐标点击（只有元素点击）
- 无按键操作、无长按、无双击
- 无截图压缩
- 无应用安装/卸载/启动
- 无 Shell 命令

---

### 8.5 claude-in-mobile

**优势：**
- **5 平台支持**（Android/iOS/Desktop/Aurora/Browser），覆盖最广
- ~40 个工具，功能最全面
- **130+ 别名**解决 LLM 工具名偏差，显著提升调用成功率
- **Flow 引擎**（batch + run）将多步操作收敛到单次 MCP 往返
- 模糊匹配（0-100 置信度评分）
- 坐标缩放系统（截图压缩后自动修正坐标偏差）
- 智能 UI 分析（标题/对话框/导航检测 + UI Diff + Action Hints）
- 稳定截图（3 次重试，< 2% 变化认为稳定）
- 差异截图（< 5% 仅文字，5-80% 裁剪变化区域，> 80% 完整截图）
- 应用商店上传（Google Play / Huawei AppGallery / RuStore）

**劣势：**
- 代码量大（8000+ 行，75+ 文件），维护成本高
- 正则解析 XML，复杂布局可能出错
- execSync 同步阻塞
- 无原生 Selector（模糊匹配不如 u2/Appium 原生可靠）
- iOS 仅支持模拟器（不支持 iOS 真机）
- WDA 依赖 Xcode 环境
- Star 较低（210）

---

### 8.6 droidrun

**优势：**
- 完整 Agent 框架（Manager/Executor/FastAgent 三模式），无需外部 MCP 客户端
- Portal App 提供高质量 UI 树（Accessibility Service）
- Portal 双通道（TCP 快速 + ContentProvider 降级），健壮
- **Stealth 模式**（Bezier 曲线 + Perlin 微抖动 + 随机延迟），反检测
- **操作轨迹录制**（RecordingDriver）
- 多 LLM 支持（6+ 供应商），按 Agent 角色分配不同模型
- 完整可观测性（Arize Phoenix + Langfuse + PostHog）
- ToolRegistry 能力过滤（自动禁用不支持的工具）
- 状态获取 7 级重试 + 恢复策略

**劣势：**
- 不是 MCP 服务器，无法被 AI IDE（Cursor/Claude）直接调用
- 需要安装 Portal App + Droidrun Keyboard
- Portal 需要 Accessibility Service 权限（部分设备受限）
- 依赖链重（LlamaIndex + httpx + arize-phoenix + textual + mcp + ...）
- iOS 支持有限（无前台应用检测，应用列表硬编码）

---

### 8.7 Open-AutoGLM

**优势：**
- **三平台支持**（Android + HarmonyOS + iOS），唯一支持鸿蒙的方案
- DeviceFactory 工厂模式，平台切换优雅
- ADB Keyboard base64 方案原生支持中文输入
- 内置敏感操作确认 + 人工接管（Take_over）机制
- 相对坐标系统（0-999），模型输出更稳定
- 50+ 中文应用映射 + 60+ 鸿蒙应用映射
- 流式推理输出，实时可见思考过程
- AST 安全解析（不用 eval）

**劣势：**
- 纯坐标驱动，**无 UI 树获取**，无元素语义定位
- 需要 VLM 模型服务（GPU 或云 API），部署门槛极高
- 需安装 ADB Keyboard APK
- 不支持 MCP 协议，无法被其他 AI Agent 调用
- 同步阻塞，无并发
- 无 App 安装/卸载
- 无录屏功能

---

### 8.8 AppAgent

**优势：**
- **探索-利用两阶段范式**，Agent 能积累操作经验（UI 元素文档）
- 反思学习机制（Act-Reflect 循环）
- SoM（Set-of-Marks）数字标注系统
- Grid 模式作为 fallback
- Prompt 设计精细（结构化输出：Observation → Thought → Action → Summary）
- 代码简洁（学术原型），易于理解和修改

**劣势：**
- 学术原型，不适合生产使用
- 仅支持 Android
- 仅 7 种基础操作（无 Home、多任务、剪贴板等）
- 无错误恢复（ADB 失败直接 break）
- 固定等待（`time.sleep()`）
- 不支持 MCP 协议
- 无应用管理
- 仅支持 GPT-4V 和 Qwen-VL 两种模型

## 十二、分散思考：进一步对比维度

### 12.1 LLM Token 消耗优化

各方案在减少 LLM token 消耗方面的设计差异值得关注：

| 优化策略 | 采用方案 |
|---------|---------|
| 截图压缩减少图片 token | mobile-mcp (JPEG 75%), android-mcp-server (PNG 80% max1280), Android-MCP (256色量化) |
| 差异截图（变化小时不返回图片） | claude-in-mobile (< 5% 变化仅文字) |
| UI 树节点过滤 | android-mcp-server, mobile-mcp, Android-MCP, claude-in-mobile |
| 复合操作减少往返 | android-mcp-server (tap_sequence), claude-in-mobile (flow_batch) |
| Action Hints 替代截图确认 | claude-in-mobile (操作后 UI diff 文字反馈) |
| 上下文图片移除 | Open-AutoGLM (推理后移除历史图片) |
